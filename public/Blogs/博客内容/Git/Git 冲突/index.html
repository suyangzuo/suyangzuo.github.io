Git冲突原创

作者： 苏扬

日期： 2026年10月17日

理解冲突

冲突的起源

冲突常见于三路合并场景，当两个提交对同一个文件的同一个地方做了不同的修改时，就会产生冲突。

不要害怕！冲突是一件很常见的事情，尤其在多人合作场景中。

如何避免冲突

为了尽量避免冲突，需要做到以下几点：

  • 单人项目，拥有多台电脑

    每次更换电脑，都要先拉取远程仓库的最新修改，然后再开始本地的工作。

  • 多人合作

    • 项目主持人制定合理、严格的合作规范，确保贡献者遵守。拒绝不合理的拉取请求。
    • 贡献者每次开始本地工作之前，都要先同步主持人与自己的远程仓库，再拉取自己的远程仓库。

说白了，就是尽量确保工作之前大家位于同一个祖先提交。

该来的总会来

多人合作时，无论主持人如何小心翼翼，也无法完全避免冲突，因此，处理冲突其实是一件很常见的事情，无需过分紧张。

处理冲突

三路合并，产生冲突

假设我们有main分支和test分支，二者拥有共同的祖先提交初始提交，并且二者都有独特提交：

此时如果在main分支使用git merge test进行三路合并，本来应该弹出文本编辑器，填写合并提交信息，但如果有冲突，就会在终端进行提示：

冲突信息翻译如下：

  • 自动合并 index.css
  • 冲突（内容）：index.css 出现合并冲突
  • 自动合并失败；修复冲突然后提交结果。

取消合并

此时工作区处于合并中状态，可以使用git merge --abort取消合并，回到合并之前的状态。

查看冲突情况

虽然之前的信息中已经提示index.css文件存在冲突，但最好还是用git status来确认情况：

红色信息显示：都修改了 index.css，因此我们要手动解决冲突。

编辑冲突文件

如果你是在VSCode的终端里运行命令，合并冲突后会自动打开冲突的文件。如果是在外部终端运行命令，就手动打开冲突的文件。任何一个文本编辑器都可以，但我仍然推荐专业的代码编辑器，比如VSCode。

只有在专业编辑器上，你才能看到采用当前更改、采用传入的更改这些鼠标可选项。

  • 采用当前更改

    ：只保留合并分支main的内容

  • 采用传入的更改

    ：只保留被合并分支test的内容

  • 保留双方更改

    ：将二者的内容都保留下来

无论怎么修改，最后都要保存文件，冲突就算处理完毕了。

提醒

无论选择哪个选项，都要检查有没有错误。如果你仔细观察，会发现图5中html和input的后标签合二为一了17行，如果选择将二者的内容都保留下来就会产生代码错误，需要手动修复。

三路合并编辑器

如果觉得传统的冲突处理界面不能满足自己的需求，可在图5中点击在合并编辑器中解决，会打开VSCode专门设计的三路合并编辑器，其功能更为强大。

三路合并编辑器的视图更为清晰，

  • 左上为传入，代表被合并分支test的内容。
  • 右上为当前，代表合并分支main的内容。
  • 下方为结果，代表合并后main分支的最终内容。

高亮的方框中就是冲突的内容，你可以手动编辑，也可以用鼠标选择高亮方框上的各种选项。最终，以下方的结果为准。编辑完毕并保存后，如果点击完成合并，则VSCode会自动暂存此文件，否则需要手动暂存。

完成合并

冲突处理完成后，文件还处于未暂存状态，可用git add resolved暂存解决冲突后的文件。当然，也可以用git add .来暂存所有改动的文件。

暂存后，就该提交了。解决冲突后可用专门的git merge --continue来进行提交。

当然，也可以用git commit提交。此时进入正常的三路合并流程，会弹出文本编辑器，让你填写提交说明：

写好后，保存文件并关闭，完成提交。

冲突已解决，合并已完成，终端显示了本次合并提交的说明。

Git Graph扩展中也显示合并已完成。
