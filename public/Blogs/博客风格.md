# 教程风格

## 核心风格

面向初学者，用中文把知识讲成一条**能理解、能操作、能观察、能验证**的学习路径。

不满足于告诉读者“是什么”，而是带着读者完整经历：

> 发现问题 → 建立直觉 → 理解原理 → 查看示例 → 动手操作 → 观察结果 → 解释异常 → 给出结论与建议

整体风格是：**口语化的表达，严谨的推理；丰富的案例，明确的观点；既讲怎么做，也讲为什么。**

---

## 一、写作定位

### 1. 读者先于知识

默认读者是初学者，或者对当前概念只有模糊印象的人。写作时始终替读者追问：

- 这个概念是什么？
- 为什么需要它？
- 它解决了什么实际问题？
- 最容易误解的地方在哪里？
- 我应该怎样操作？
- 怎么确认自己做对了？
- 出错以后怎么办？

不因为某个概念“很基础”就跳过。真正需要省略时，给出前置教程或对应章节，而不是让读者自行猜测。

### 2. 经验与依据并重

文章带有鲜明的个人实践经验，可以明确写“我推荐”“我个人更喜欢”“我在实际使用中遇到过”。但个人偏好不能冒充普遍规律：

- **事实**：尽量用官方文档、规范、实际运行结果支撑。
- **经验**：说明自己的使用场景和理由。
- **建议**：说清适用条件，不把一种方案写成唯一答案。
- **观点**：允许鲜明，但要让读者知道判断依据。

### 3. 以解决问题为终点

教程不是为了堆砌术语，而是为了让读者能够解决实际问题。即使讲历史、原理或数学公式，最终也要回到理解、操作、判断或应用上。

---

## 二、整体结构

### 1. 常见的章节顺序

根据题材取舍，但通常沿着以下顺序展开：

1. **概念或背景**：是什么、从哪里来、为什么出现。
2. **用途或问题**：解决什么需求，适用于哪些场景。
3. **核心原理**：本质、组成、规则、必要条件。
4. **案例或操作**：用同一个具体案例逐步实现。
5. **结果验证**：展示运行结果、界面变化或实际效果。
6. **异常与陷阱**：展示错误、反例、边界情况和常见误解。
7. **总结或建议**：压缩成一句话、一组规则或明确的选择建议。

最常用的内在逻辑是：

> 是什么 → 为什么 → 怎么用 → 结果如何 → 为什么出现这个结果 → 如何改进

### 2. 标题层级清楚

- 二级标题表示一个完整阶段，如“基本概念”“安装与配置”“常见问题”。
- 三级标题只解决一个具体问题，如“什么是热区”“如何获取进程 ID”。
- 四级标题用于并列方案、列表中的重点项或更细的分类。
- 标题优先使用明确的名词短语或问题，不写空泛的“概述”“其他内容”后却混入无关知识。

每一节只承担一个主要任务。小节宁可多一些，也不要把定义、步骤、原理和注意事项挤在同一段里。

### 3. 开头直接进入问题

不使用宏大、空泛的序言。常见开头有：

- 一个具体需求：“假设我们希望查询结果按照中文姓名排序。”
- 一个反常识现象：“同样的小数，四舍五入的结果却不一致。”
- 一个直观对比：“先观察 2D 和 3D 旋转的区别。”
- 一个读者正在经历的错误：“有时候，我们会看到端口已被占用。”
- 一个简短定义，随后立刻举例：“热区，即能够触发事件的区域。”

背景和历史可以写，但要服务于当前主题。它们用于解释技术为何形成、不同方案为何存在，而不是单独展示资料储备。

### 4. 前后章节形成连续路径

后文应利用前文已经建立的案例和概念，少用互不相干的小例子。需要回顾时，用“如前所述”“回顾第 2 节”“还记得前面的……吗”自然衔接。

对于已经讲过的操作，可以写“与前文相同，不再赘述”，并给出对应章节；对于尚未讲到的内容，可以明确告诉读者后文会解决，避免疑问悬置。

## 三、讲解节奏

### 1. 用提问推动文章

提问不是装饰，而是下一小节要真正回答的问题。常见节奏是：

> 假设有这样一个案例 → 运行之后出现了什么？ → 为什么会这样？ → 如何解决？ → 修改后再次验证

常用提问方式：

- “问题来了：……”
- “为什么会这样？”
- “那应该怎么办呢？”
- “二者有什么区别？”
- “如何确认操作成功？”
- “如果换成另一种情况呢？”
- “这真的是我们想要的结果吗？”

提出问题以后，要尽快给出实验、推理或答案，不连续堆砌没有实际作用的提问。

### 2. 先观察，再下结论

尽量让读者先看到现象，再引出抽象规则：

1. 给出一个最简单的例子。
2. 展示实际结果或效果。
3. 指出结果中值得注意的部分。
4. 解释产生结果的机制。
5. 最后概括规则。

这种写法比先摆出一整套抽象定义更符合你的教程风格。

### 3. 每次只改变一个关键条件

复杂问题采用递进式实验：

- 先写最简版本。
- 引入一个新需求。
- 暴露当前版本的问题。
- 只修改关键代码或选项。
- 对比修改前后的结果。
- 再进入下一个问题。

不要一开始就给出最终完整方案，再逐行解释。让读者看到方案是如何被问题一步步“逼出来”的。

### 4. 持续使用同一案例

同一篇文章尽量围绕同一组对象展开，例如同一批分支、同一个数据库、同一个滑块、同一个图形或同一个软件。读者不必反复熟悉新背景，就能把注意力放在概念变化上。

案例要具体：使用实际的名称、数值、路径、端口、字段和命令，少用长期没有语义上下文的 `foo`、`bar`。

### 5. 对比是重要的解释工具

遇到相似概念时，优先从以下角度对比：

- 定义与本质
- 相同点与不同点
- 是否可读、可写、可见、可交互
- 适用范围与限制
- 性能、安全、兼容性、可维护性
- 临时方案与永久方案
- 默认行为与自定义行为

对比之后要给出一句容易记住的结论，而不只是留下一张表。

## 四、语言与语气

### 1. 像在旁边带读者做实验

自然使用三种人称：

- **“我们”**：共同分析、共同操作，如“我们先来看看……”。
- **“你”**：指出读者会观察到的现象或需要完成的动作，如“你会发现……”。
- **“我”**：交代真实经验、选择和踩坑经历，如“我个人更推荐……”。

整体像一位有经验的人坐在旁边演示，而不是站在讲台上宣读教材。

### 2. 口语化，但不松散

允许使用“问题来了”“其实很简单”“这回正常了”“别担心”“没错”等口头表达，让文章有节奏、有情绪。但每个轻松段落之后，仍要回到准确的技术解释。

可以适度幽默、调侃或使用表情符号，尤其在展示意外结果时；它们只能调节节奏，不能替代原因分析，也不宜每段都出现。

### 3. 句子直接，段落聚焦

- 优先使用主动句和明确动词：“调用函数”“修改选项”“观察结果”。
- 一段只表达一个中心意思。
- 长句可以拆解为“现象—原因—结论”三部分。
- 少用空洞的形容词，多写可观察的差异。
- 技术内容准确，但不刻意制造学术腔。

### 4. 用连接词呈现推理

高频且符合风格的衔接方式包括：

- 补充：**此外、同时、不仅如此**
- 转折：**然而、但是、问题是**
- 因果：**因此、所以、这意味着**
- 举例：**比如、举个例子、假设**
- 总结：**简而言之、换句话说、由此可见**
- 回顾：**如前所述、前面已经提到**
- 推进：**接下来、此时、现在**

这些词要真实反映逻辑关系，而不是机械地放在段首。

### 5. 把关键结论写得鲜明

常用对照、判断或短公式压缩知识，例如：

- “节点不一定是元素，但元素一定是节点。”
- “数组名称可以读，不能改写。”
- “只有先保存数据，才能读取数据。”
- “拉取 = 提取 + 合并。”

重点落在“必须”“只能”“不会”“并非”“默认”“等价于”等边界词上。该强调时要明确，不让读者自己从长段中寻找结论。

### 6. 中英文术语自然配合

以中文解释为主，首次出现的重要术语可以附英文、缩写或全称：

- 先给中文含义，再给英文名称。
- 缩写需要展开时，说明字母分别代表什么。
- 同一个概念在整篇文章中保持名称一致。
- 代码、命令、属性名、参数和文件名保持原样，不为了中文化而改写成不可执行的形式。

## 五、案例、代码与图像

### 1. 每个重要知识点形成验证闭环

最典型的表达单元是：

> 操作或代码 → 实际结果 → 解读结果 → 得出规则

不能只有代码没有结果，也不能只有截图没有解释。读者应当知道：要做什么、会看到什么、为什么说明做对了。

### 2. 代码和命令必须服务于当前问题

- 先交代代码的目标和运行环境。
- 示例保持最小化，但关键步骤不能省略。
- 注释使用简洁中文，解释意图或关键规则。
- 占位内容尽量具体，如“本地分支名称”“远程仓库名称”。
- 同一案例中的变量、文件名、数据库名和分支名保持连续。
- 一个函数有多种重载或一个命令有多个参数时，按使用场景分别说明。

代码之后可以指出关键行，但不要逐行复述已经一目了然的语句。

### 3. 主动展示错误和反例

你的教程不仅展示正确做法，还经常故意写一次“看似合理”的错误方案：

1. 展示直觉写法。
2. 展示报错、异常数据或不符合预期的效果。
3. 必要时翻译错误信息。
4. 解释真正原因。
5. 给出修正方案并再次验证。

这种“先暴露问题，再解决问题”的过程，是风格中最重要的一部分。

### 4. 图像是证据，不是装饰

截图、示意图、动画和交互演示应承担明确任务：

- 图前告诉读者要观察什么。
- 图后指出红框、箭头、数值、顺序或界面变化。
- 需要时明确写“从图中可以看出……”。
- 同一个操作有多个阶段时，按实际顺序配图。
- 能用交互演示观察的概念，优先让读者亲手调整参数，再解释规律。

不要让读者看到图以后仍然不知道它证明了什么。

### 5. 表格和列表用于压缩信息

- 类型、参数、权限、格式、优缺点等并列信息适合表格或列表。
- 操作步骤适合有序列表。
- 相互独立的特点适合无序列表。
- 列表不宜过碎；如果需要连续因果推理，仍用正文段落。

表格之后补一句“如何选择”或“这说明什么”，把资料转化为判断。

## 六、引用、链接与技术边界

### 1. 重要结论尽量有出处

常引用官方文档、W3C 规范、MDN、项目官网或官方仓库。引用方式通常是：

> 先提出疑问 → 查看权威资料 → 摘出关键描述 → 用自己的话解释 → 回到当前案例

不整段搬运资料，也不让外链代替自己的讲解。

### 2. 内部教程互相衔接

涉及已经写过的前置知识时，直接链接到相关专题或具体章节。文章只展开当前主题新增的内容，避免重复整套基础教程。

### 3. 明确版本、平台和时效性

涉及安装、界面、参数、兼容性、废弃特性或政策时，尽量说明：

- 操作系统与软件版本
- 默认路径或默认配置
- 新旧版本差异
- 是否已废弃
- 是否只适用于特定平台
- 信息是否可能随时间变化

旧内容失效时，明确标记，不让读者把历史做法当成当前规范。

## 七、观点、推荐与风险提醒

### 1. 推荐必须有理由

不要只写“推荐使用 A”，而要写清楚：

- A 解决了什么痛点。
- B 在什么场景下更合适。
- 二者在性能、安全、便利性、兼容性上的取舍。
- 自己的选择基于什么使用环境。

你常表达“没有绝对好坏，只有是否适合实际需求”，但这不妨碍在明确场景下给出强烈推荐。

### 2. 默认选项与关键选项分开

安装和配置类教程中：

- 无特殊需求可保持默认的选项，直接写“默认即可”。
- 会影响安全、兼容性、数据或后续工作的选项，展开解释。
- 有多个安装方式时，说明区别并给出偏好。
- 操作完成后提供版本查询、状态查看或实际运行等自检方式。

### 3. 风险提醒要具体且前置

删除、格式化、覆盖、强制操作、权限和数据库相关操作，要在执行前提醒：

- 会影响哪些数据或环境。
- 是否可逆。
- 是否需要备份。
- 是否可以先用预览模式确认。
- 失败以后如何取消或恢复。

必要时使用“慎用”“务必”“千万不要”等强语气，但强提醒只用于真正的风险，避免全文都在警告。

### 4. 提醒块各有职责

常见类型包括：

- **提醒**：补充容易忽略的规则或副作用。
- **注意**：指出当前步骤中的关键限制。
- **小知识**：补充背景、词源、历史或相邻概念。
- **总结**：把一段复杂内容压缩成可记忆的结论。
- **重要／超级提醒**：只用于严重风险或必须遵守的规则。

提醒块应短而准，不要在“提醒”里重新展开一整篇离题教程。

## 八、不同题材的典型写法

### 1. 概念型教程

> 一句话定义 → 生活或软件类比 → 具体案例 → 观察结果 → 原理 → 相似概念对比 → 陷阱 → 一句话总结

类比用于建立直觉，随后必须回到技术定义，避免把类比本身当成原理。

### 2. 操作型教程

> 目标与适用场景 → 准备工作 → 按界面顺序逐步操作 → 每步配图 → 验证是否成功 → 常见错误与处理

步骤顺序要符合真实界面和真实工作流，不能只按命令分类重新排列。

### 3. 原理型教程

> 直观现象 → 提出问题 → 必要条件或公式 → 代入具体数值 → 实验验证 → 边界条件 → 实际应用

公式之后要解释每个参数的意义，并用一个简单案例算一遍。数学内容最终要服务于代码或视觉结果。

### 4. 工具推荐型教程

> 历史与现状 → 当前痛点 → 候选工具对比 → 明确推荐及理由 → 下载安装 → 核心用法 → 验证与注意事项

可以写工具生态、行业背景和个人经验，但最终要让读者知道“我该选哪个，以及为什么”。

### 5. 排错型教程

> 还原错误场景 → 展示原始错误 → 翻译或提炼关键信息 → 定位原因 → 给出最小修复 → 再次运行 → 补充预防方法

不要跳过诊断直接给命令。读者需要学会下一次自己判断。

## 九、可复用的段落句式

以下句式体现风格，但应按需使用，不要机械重复：

- “假设我们有这样一个需求：……”
- “先来看看最直接的做法。”
- “运行之后，你会发现……”
- “问题来了：为什么会这样？”
- “这并不是我们真正想要的结果。”
- “要理解这一点，就要先弄清楚……”
- “举个例子：……”
- “我们换一个条件，再试一次。”
- “从图中可以看出……”
- “这就证明了……”
- “解决方法其实很简单：……”
- “修改之后，再次运行，结果符合预期。”
- “简而言之：……”
- “这两种方案没有绝对好坏，取决于实际需求。”
- “我个人更推荐……，原因是……”
- “注意：这条规则只在……条件下成立。”

## 十、默认写作模板

```markdown
## 主题或阶段

### 是什么／为什么需要

用一个具体场景或反常识现象开场，再给出简短定义。

### 最简案例

给出最小代码、命令或操作。

展示运行结果，并指出最值得观察的部分。

### 为什么会这样

解释底层机制，必要时配合示意图、公式或权威资料。

### 如何改进

针对前面暴露的问题修改一个关键条件。

展示修改后的结果，确认问题已经解决。

### 注意／提醒

说明边界条件、默认行为、版本差异或风险。

### 总结

用一两句话写出读者真正需要记住的规则。
```

不是每篇文章都要保留全部小节；真正需要保留的是这条认知顺序。

## 十一、HTML 页面组织习惯

如果需要把教程写成本项目的 HTML 页面，沿用既有结构：

- `article.专题简介`：标题、原创标记、作者、日期和联系方式。
- `div.专题正文区`：整篇教程正文。
- `article.正文分区`：一个主要章节，通常对应一个 `h2`。
- `h2.分区标题.分区2级标题`、`h3.分区标题.分区3级标题`：组织章节与具体知识点。
- `p.分区普通文本`：概念解释、案例分析和结果解读。
- `ul.分区列表`、`ol.分区列表.有序列表`：特点、对比和操作步骤。
- `pre > code`：代码与命令，使用对应语言类名。
- `figure.截图容器`：截图、动画和示意图；图像应有有意义的 `alt`，必要时用 `data-desc` 补充说明。
- `section.提醒`：提醒、注意、小知识或阶段总结。
- `span.专业名词`：带底色和边框的名词标签，用于列表项主题、要点名称、结论等需要突出显示的术语。
- `span.行内专业名词`：融入正文句子的专业名词，仅用颜色和字体加以区分，不使用标签式底色。
- `span.代码`：带深色底色的代码标签，用于需要突出显示的命令、表达式、属性、函数或界面文本。
- `span.行内代码`：融入正文句子的简短代码、变量、参数、数值或扩展名，仅用等宽字体和颜色加以区分。
- `span.强调`、`span.附加说明`：分别标出关键判断和补充信息。

HTML 结构服务于阅读顺序，不用复杂排版掩盖讲解上的跳跃。

## 十二、完成前的自检

写完以后，逐项检查：

- 开头是否快速进入了真实问题，而不是空泛介绍？
- 每个抽象概念是否有例子、类比、图示或实验支撑？
- 是否让读者看到了结果，并解释了结果说明什么？
- 是否回答了初学者最可能提出的“为什么”和“怎么办”？
- 是否至少检查了一个容易出错或被误解的边界情况？
- 代码、命令、路径和参数能否在当前案例中连贯使用？
- 图像是否都有明确的观察目的和图后解读？
- 推荐方案是否说明理由、条件和取舍？
- 危险操作是否在执行前提醒，并提供验证、备份或恢复思路？
- 外部事实是否有可靠出处，个人经验是否被明确表达为经验？
- 是否留下了可以单独记住的一句话结论或操作规则？
- 删除幽默、表情和口语句以后，技术推理是否仍然完整？

## 一句话仿写要求

> 用中文面向初学者写作，以具体问题开场，用“我们”带着读者做实验，用“你”指出可观察的结果，用“我”分享有依据的经验；通过连续提问和正反案例逐步推进，先观察再解释，最后给出鲜明结论、适用条件和必要提醒。
